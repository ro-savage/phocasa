## Migration evidence

1. **Automatic lightweight migration passes** all three `MigrationTests`. In the migrated store's SQL, `ZISDELETED`
   becomes `ZISINBIN` with the same rows set, and `ZPHOTOASSET.ZTHUMBNAILDATA` and `ZTAG.ZPARENT` are dropped.
2. **`originalName` is load-bearing (mutation check).** Without it, all three tests fail: the container doesn't
   open, with `NSCocoaErrorDomain 134110 "Cannot migrate store in-place: Validation error missing attribute values on
   mandatory destination attribute" {entity=PhotoAsset, attribute=isInBin}`. In the app that would be the
   container's `fatalError` at launch.
3. **One-off check against `main`'s real models** (not committed):
   - Setup:
     - `main` at `1d91126` was exported to `$TMPDIR/phocasa-31-main`;
     - a temporary test there wrote a store with the **real** models: 30 photos, 10 binned, tags including a child
       tag, a 256 KB `thumbnailData`, a library and a preset;
     - a temporary test on this branch wrote the same kind of store with the frozen `PhocasaSchemaV1`.
   - The two stores' SQLite DDL is **identical**, and so are the `NSStoreModelVersionHashes` in their `Z_METADATA`.
     `PhocasaSchemaV1` is exactly the format real libraries are in.
   - A copy of the store `main` wrote, opened with this branch's models, kept every value: all 30 photos' fields, the
     10 bin flags, tags and links, the library and the preset.
   - All of it was deleted afterwards.
4. **Downgrade (probe, not committed).** A store migrated by this build opens with the frozen V1 models: Core Data
   infers the reverse rename, and the bin flag survives. A row binned there then shows up in the bin when this build
   opens the store again. So an older build still works on a migrated library, bug included. It would lose nothing
   except the dropped fields, which were always empty.
5. **An orphaned file, harmless.** A `thumbnailData` blob held in external storage stays in
   `.default_SUPPORT/_EXTERNAL_DATA` after the migration. Core Data doesn't delete it. The app never wrote
   `thumbnailData`: git history shows it was only ever read, and `76a5b11` removed that read. So real libraries have
   no such files.

## Findings

1. **The bug is wider than rating right after binning.** A photo that was already in the bin when the library loaded
   (binned in an earlier session) keeps its flag through the first save: the fetch sets the value. The save after
   that reads the stale `false` and writes it. So on `main`, rating a binned photo twice, or rating and then tagging
   it, takes it out of the bin. `testRatingAPhotoBinnedEarlierTwiceKeepsItInTheBin` covers this.
2. **Leftover uses of the old name still compile after the rename, and misbehave.** `isDeleted` now resolves to
   SwiftData's own `PersistentModel.isDeleted`, an extension member, not a protocol requirement. A probe (not
   committed) showed:
   - `photo.isDeleted` reads `false` for a binned photo;
   - `#Predicate { $0.isDeleted }` compiles and **crashes the process** at fetch time:
     `SwiftData/DataUtilities.swift:85: Fatal error: Couldn't find \PhotoAsset.isDeleted on PhotoAsset`.

   An `@available(*, unavailable, renamed: "isInBin")` shadow on `PhotoAsset` doesn't help, because overload
   resolution falls through to SwiftData's member (tried; reverted). A deprecated forwarding alias would bring back the
   hiding that spec §H5 objects to, so I didn't add one. **When the coordinator merges 32, 33 and 35, a `grep` is the
   guard** (see Needs).
