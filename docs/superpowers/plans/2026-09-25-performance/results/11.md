### How it works

- **Scheduler.**
  - One lock guards a LIFO stack of pending keys, `[Key: Entry]` (waiters keyed by a per-caller token, plus a
    `started` flag) and a running count.
  - `value(for:work:)` wraps `withCheckedContinuation` in `withTaskCancellationHandler`.
    - A cancelled caller is resumed with `nil` at once.
    - A key whose callers have all been cancelled before it starts is dropped from the stack, so its work never runs.
  - Work runs on `DispatchQueue.global(qos:)` inside an `autoreleasepool`. When it finishes, the scheduler resumes the
    remaining waiters and starts the newest pending key.
- **`ImageLoader.loadThumbnail`.**
  - It rounds `maxSize` UP to a bucket in `[256, 384, 512, 768, 1024, 1536]`, then checks the cache. A cached bucket
    up to 2× larger also counts.
  - On a miss it calls `scheduler.value(for: (path, bucket, generation))`, with `activeProcessorCount` workers at
    `.userInitiated`.
  - The work closure decodes, wraps the result in an `NSImage` and stores it in the cache (cost =
    `bytesPerRow × height`, `totalCostLimit` = 512 MB). All callers therefore share one `NSImage` instance, and a
    decode that finishes after its cell scrolled away still lands in the cache.
- **Decode** (`decodeThumbnail(at:maxPixels:preferEmbedded:)`) always passes `ThumbnailMaxPixelSize`, `WithTransform`
  and `ShouldCacheImmediately`.
  - **RAW** (`FolderScanner.rawExtensions`): tries `FromImageIfAbsent` first, and falls back to `FromImageAlways`
    when the embedded preview's long edge is below 0.75 × the bucket.
  - **Everything else:** `FromImageAlways`.

### Grid observations (hosted `PhotoGridView`, in-memory library, local probe, not committed)

This is the real `PhotoGridView` with a view model over 2,000 in-memory photos, all pointing at one tiny temp JPEG
(so layout is measured, not decoding), in a 1200×800 window with 6 columns. It is main-thread CPU for the whole phase,
including the run-loop turns in between. Two alternating rounds, load 3–4:

| Phase | main | branch |
|---|---|---|
| 30 resize steps, 2 pt apart, within one bucket, fresh | 366 / 390 ms | 388 / 367 ms |
| 90 page scrolls (800 pt each, about 30 new cells per page) | 5,206 / 5,097 ms | **3,625 / 3,502 ms** (−31%) |
| 30 resize steps right after those scrolls | 869 / 855 ms | 967 / 979 ms (**+13%**) |

- **Page scrolls.** Synchronous layout plus display per page is 36–40 ms on main and 31–34 ms on the branch, the
  same at 2k and 10k photos. It's roughly 1 ms per newly created cell: `LazyVGrid` cell creation, not N, is the cost.
  At 120 Hz a fast scroll that brings in one or two rows per frame (6–12 cells) spends 6–12 ms, which is borderline.
  That's the number to watch before deciding on `NSCollectionView` after waves 1–2. At this point it doesn't justify
  one.
- **Trade-off: resizing right after a long scroll.** It costs 13% more main-thread CPU, almost all in the first four
  resize frames (≈120/80/64/44 ms against ≈100/30/26/25 ms on main). Variants isolate the cause: showing a cached
  thumbnail in a newly created cell's first frame (`cachedThumbnail` in `body`). Without it (old cell layout, no
  lookup) resize-after-scroll matches main, but scrolling loses its whole gain (5,060–5,240 ms) and scrolled-back
  cells flash the placeholder for a frame. Moving the lookup to `.onAppear` kept the resize cost and gave back half
  the scroll gain (4,513–4,657 ms). Moving it to `init` performed the same as `body`, and `body` is simpler. I kept
  the scroll gain, and I'm recording this here as a known regression on that one path.
- **Fresh resizes** cost the same on both. On main they restarted every visible cell's `.task` on every step (cache
  hits, but restarts); on the branch they don't.

## Deviations from the task file

1. **Click wiring** (Step 6). The task file's wiring (`onTapGesture(count: 2)` + `simultaneousGesture(TapGesture())`)
   makes a click on a star also select the photo, and its cell still waits out double-click detection for the star.
   I used a plain `onTapGesture` for select, a `simultaneousGesture(TapGesture(count: 2))` for open, and a
   high-priority no-op double-tap on the rating row. That keeps both star behaviours exactly as they were (see the
   table above).
   - Because the tests need to drive the real cell, the gestures now live inside `PhotoGridItemView`, which takes
     `onSelect`/`onOpen` closures.
   - `handleSelectionClick` (today's `NSEvent.modifierFlags` logic) stays in `PhotoGridView`.
2. **Square thumbnail.** It is `Color.clear.aspectRatio(1, contentMode: .fit)` with the image in an overlay, not a
   frame computed from the cell width. The grid can only estimate the real column width, because `.padding()`'s
   default isn't exposed, so a computed fixed frame could overflow or leave gaps. The aspect-ratio square takes its
   size from the proposed column width alone and never measures the image. The `minWidth/minHeight: 60` floor from
   main is kept.
3. **Grid bucket input.**
   - It is computed from the drawn thumbnail width (`cellWidth − 12` for the cell's padding) × `displayScale`, not
     from `cellWidth`.
   - The old `max(300, …)` floor is gone, so small cells (many columns) use the 256 bucket.
   - `thumbnailBucket(gridWidth:columns:displayScale:)` is a `nonisolated static` function, so it can be tested.
4. **Bucket rounding.** Requests round to the nearest pixel before rounding up to a bucket. With that half-pixel
   tolerance, floating-point noise such as 384.0001 can't jump a whole bucket.
5. **Cache reuse across buckets.** A cached thumbnail from a bucket at most 2× larger serves a smaller request, so
   zooming the grid out is instant. The 2× limit keeps downscaled drawing from aliasing.
6. **Generations** (not in the task). `invalidate(path:)` bumps a per-path generation and `clearCache()` bumps an
   epoch. The scheduler key includes the generation, and the store is checked under the same lock. So a decode that
   was running when the path was invalidated can't put the stale thumbnail back, and a request made after
   invalidation never joins the stale decode.
7. **Where caching happens.** The scheduler's value is `CGImage`, as specified, but the work closure itself creates
   the `NSImage` and caches it. Callers return the cached instance, so waiters share one `NSImage`, and a decode whose
   cell scrolled away mid-decode isn't wasted.
8. **Scheduler extras.**
   - Re-requesting a pending key moves it to the top of the stack: it is the newest request.
   - Cancellation races are resolved by checking `Task.isCancelled` under the lock inside the continuation body.
     Cancellation sets the flag before its handler runs, so no per-token cancel bookkeeping is needed.
   - A cancelled caller whose work has already started is resumed at once. It doesn't wait for the work.
9. **New API `cachedThumbnail(for:maxSize:)`:** a synchronous cache lookup, bucket-aware. The grid uses it for the
   first frame. Task 12 can use it for an instant detail-view placeholder.
10. **Scheduler benchmark details.** "80 ms decodes" are 80 ms of thread CPU time, not sleeps: with sleeps, the
    unbounded FIFO would also finish in 80 ms and the comparison would mean nothing. Cells more than 40 behind are
    cancelled, as in the grid and in the coordinator's protocol.
11. **Extra tests** beyond the task's list (see "Tests added"), including a new test file,
    `PhotoGridItemViewTests.swift`, for the grid's bucket and click behaviour.
12. **`testLoadFullResolutionIsUnchanged`** pins `loadFullResolution`'s current output: unrotated, spec §D1. When
    task 12/22 fixes orientation in the detail view, whoever changes `loadFullResolution` updates this test.

## Follow-ups

- **Star-click latency (pre-existing, ≈356 ms).** A click on a star rating in the grid waits out double-click
  detection, on main and here. It could be made instant by dropping the rating row's double-tap guard in
  `PhotoGridItemView`, at the cost of a double-click on a star rating twice (set, then clear). That's a product
  decision; `RatingView` itself isn't owned by any wave-1 task.
- **The resize-after-long-scroll trade-off** (above). If it matters, the Instruments question is why `LazyVGrid`
  builds more cells on the first resize frames after a long scroll when the first frame shows the image.
- **Large-cell JPEG buckets (768+)** hit the serialised hardware decoder for big JPEGs (16 ms per image against
  11 ms at ≤ 512 for 24 MP files). If users favour 2–3 columns, consider decoding at `min(bucket, longEdge ÷ 8)` when
  that is ≥ 0.75 × bucket.
- **`LazyVGrid`** creates cells at ≈1 ms each (see "Grid observations"). Revisit `NSCollectionView` only if the real
  app, after waves 1–2, drops frames while scrolling.
- `PhotoAsset.thumbnailData` is still dead (task 31).
