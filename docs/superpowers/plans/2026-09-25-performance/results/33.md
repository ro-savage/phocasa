### How the backfill works

1. `setModelContext` → `backfillCaptureDatesAfterScans()`. It waits for `waitForScans()` (the launch rescan and
   anything queued behind it), then `startDelay` (2 s), so it doesn't compete with the launch's thumbnail decodes.
   - It holds the store weakly while waiting: a window closed meanwhile does nothing.
   - It then waits for scans again.
2. **Off the main actor, utility QoS:**
   - a background context fetches `captureDate == nil && fileSize > 0` (id and paths only);
   - `concurrentPerform` reads each candidate's JPG, or its RAW if the JPG can't be read.
   - Rows whose files were empty at the last scan are skipped: they can't hold a date. This also keeps the benchmark
     harness's empty seed files from being read on every launch.
3. **Off the main actor:** the ranks of every row under the new keys, planned from a plain-value snapshot
   (`LibrarySort.ranks(of:)`).
4. **On the main context,** because of the background-context rule:
   - each chunk fetches its rows by id, sets only a nil `captureDate`, and saves;
   - chunks grow below 11 ms and shrink above 15 ms, and the backfill sleeps as long as each chunk took between them.
   - A save costs about 7 ms at 10k loaded photos however few rows it writes (`setRating` pays the same), plus about
     0.13 ms per row. So chunks settle at about 30 rows at 10k.
5. **Once, on the main actor:** `LibrarySort.reorder` places every list element by its planned rank (hash lookups,
   no model reads), merges in photos the plan didn't know by key, bumps the versions and calls
   `refreshVisiblePhotos()`.
   - Until then the lists keep the old order, so the order changes once.
   - A photo moved or added during the backfill keeps its change: chunks look rows up by id, and unknown photos are
     merged by key.

Files with no capture date, and files that can't be read, get nothing written. They are read again on the next launch:
0.40 s in the background for 10k such rows, with no main-actor work.

## Deviations from the task file, and why

1. **One attribute, not two.**
   - The task allowed a second attribute so the backfill doesn't re-read undated files every launch. I built it
     (`captureDateChecked: Bool = false`), then measured the schema alone.
   - It doubled the column's cost: fetch- and save-bound lines went from +2–5% to +5–13% (tables above). That's
     permanent, on every launch, reload, scan and save.
   - Without it, files with no capture date (and unreadable ones) are re-read on each launch: about 0.4 s in the
     background for 10k such rows, with no main-actor work and nothing written.
2. **Option (b), sorting in memory, but without a full sort.**
   - A stored non-optional `sortDate` would need a write to every row, dated or not. Until the backfill finished, it
     would also need the same in-memory fix-up.
   - A full in-memory sort reads 1–2 model properties per photo (about 10–19 ms at 10k) on every load.
   - Instead SQLite sorts by `(captureDate, creationDate)`, which yields two sorted runs, and the fetch merges them
     reading about 14 properties when either run is empty. That is the state of every library before the backfill and
     of most after it.
   - It lives inside `fetch(where:in:)`, so task 32's background snapshot gets the order too. It depends on SQLite
     putting NULLs first ascending and last descending; tested both ways, in-memory and on disk.
3. **Ties are broken by creation date** (`LibrarySort.Key`). With one-second EXIF resolution, ties are common (bursts).
   Without a tie-break, a restored burst frame would move to the end of its burst, while a fresh fetch put it back.
4. **The parser and ImageIO extraction are in a new `Services/CaptureDate.swift`.** `MetadataService` changes only in
   `readMetadata`/`PhotoMetadata`. `CaptureDate.read(from:)` is the backfill's date-only read, which skips the sidecar
   and keyword work.
5. **ImageIO's metadata tree has no `exif:DateTimeOriginal`.** It maps the EXIF value to `photoshop:DateCreated`
   (ISO 8601, subseconds merged), which `CGImageMetadataCopyTagMatchingImageProperty` finds. So the parser accepts XMP's
   ISO forms as well as EXIF's. A file whose own XMP holds `photoshop:DateCreated` (Lightroom, Photoshop) gets that
   value, which by the MWG mapping is the same date.
6. **The backfill waits 2 s after the launch scans, and skips rows with `fileSize == 0`.** Both came from the full
   suite:
   - Before the delay, a finished test's backfill ran its background fetch after `tearDown` deleted that test's
     store: 18 CoreData I/O-error log lines.
   - The empty-file rule keeps the harness's empty seed files out of every launch.
7. **Chunks are sized by time, and sleep as long as they took.** The task said "chunks of at most ~16 ms"; a fixed row
   count can't give that when a save's fixed cost scales with the loaded library. The sleep instead of a yield gives
   the run loop half the main actor while the backfill writes.
8. **The re-order at the end uses ranks planned off the main actor** (`LibrarySort.ranks`/`reorder`) rather than
   re-sorting with model reads: 5.4 ms at 10k.
9. **The bin test needed no `XCTExpectFailure`.** A probe on this branch:
   - rating a binned photo loses its bin flag in the store;
   - so does writing to the same object right after `moveToBin`;
   - writing after a fetch by id keeps it, and that is what each backfill chunk does.

   So "binned rows stay binned" passes strictly on both sides of task 31's rename.
10. **Reading tests are in my new `CaptureDateReadingTests`,** not `MetadataParsingTests`, to keep clear of other
    tasks' files.

## Follow-ups

- **Undated files are re-read on each launch** (about 0.4 s in the background per 10k). If that matters for libraries
  of screenshots or scans, a sentinel date or a separate table could mark them without a `PhotoAsset` column. Both
  cost complexity; a column costs every fetch.
- **The backfill runs only after launch.** A file that couldn't be read then (an offline drive) gets its date at the
  next launch, not when a later rescan finds it. Calling `backfillCaptureDatesAfterScans()` after scans that change the
  missing set would close that.
- **Multiple windows:** each window's view model runs its own backfill, as each runs its own launch rescan. They write
  the same values; the second finds nothing to do if it starts later.
- **Not read:** capture dates in XMP sidecars (Lightroom's "Edit Capture Time" writes there), and `DateTimeDigitized`
  for scans.
- **A partially copied file** read by a scan gets no date, like its rating and keywords. The backfill retries it next
  launch because its date is nil.
- **A half-dated library's `loadExistingData`** is +5% (the linear merge). Galloping, which binary-searches runs,
