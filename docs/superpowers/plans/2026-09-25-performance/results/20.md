### How a scan works now

1. `scanFolder` sets `isScanning = true` synchronously. If a scan is running, it records the folder and returns; the
   running scan's loop picks it up next. Repeated requests coalesce, and the latest folder wins.
2. On the main actor, the scan saves the context if it has pending changes (another context can't see unsaved
   changes).
3. **Off the main actor, concurrently:** the stored rows are read through a background context (≈ 270 ms per 10k
   rows) while the folder is walked (≈ 160 ms per 10k files). Then `ScanPlan` diffs them. Rows the scan didn't find
   are `stat`ed, and marked missing only if none of their files exists.
4. **Off the main actor:** metadata is read for new photos only, across all cores. `scanProgress` shows
   "Reading metadata for N new photos... d/N".
5. New photos without keywords are inserted and saved through a background context. They link to nothing, so they
   touch no row the view model's context holds (see deviation 3).
6. **On the main actor:**
   - rows whose values changed are fetched by `id` in one fetch, and only fields that differ are assigned;
   - new photos with keywords are inserted with one tag dictionary (`Tag.parse` plus one `FetchDescriptor<Tag>` per
     chunk of 256), saving and yielding between chunks;
   - `missingPhotoIDs` is set, `lastScanDate` is set, and the context saves if it has changes.
7. `loadExistingData()` runs only if the scan inserted photos, took a photo out of the bin, or changed the missing set.
   If only paths or sizes changed, `photosDidChange(_:)` patches the in-memory library instead. An unchanged rescan
   writes no photo row and doesn't reload.

## Deviations from the task file, and why

1. **`7x` doesn't measure what the task file says.**
   - The seed stores `/var/folders/…` paths: `resolvingSymlinksInPath()` strips `/private`. The folder enumerator
     reports `/private/var/folders/…`.
   - So `7x`'s warm-up run inserts a second row for every file, on `main` too: the info line gives `stored rows=20000`
     on both. The timed runs rescan 10k matching rows plus 10k stale ones.
   - The spec's 2,433 ms baseline was measured the same way.
   - On the branch, the background read of 20k rows (about 540 ms) bounds `7x`'s wall time.
   - I left `7x` alone, since the coordinator compares it between branches, and added `7w`, which seeds under the
     scanner's own paths.
2. **The row comparison is fully off the main actor, and the main actor looks rows up by `id`.**
   - The coordinator suggested reading plain values in a background `ModelContext`, which I did. On the main actor, I
     fetch only the changed rows in one `#Predicate { ids.contains($0.id) }`, instead of calling `model(for:)` per
     `persistentModelID` (probe: 2.5 ms per 10 lookups).
   - Bin membership comes from a `#Predicate { $0.isDeleted }` fetch, not from the property, because reading
     `isDeleted` through a model can be stale (task 10's deviation 12). `applyScanUpdates` writes `isDeleted = false`
     without comparing it first, for the same reason.
3. **New photos without keywords are inserted through a background context.** The task file said to insert on the
   main actor.
   - **Why:** on the main context, inserting and saving 1k rows costs about 130–150 ms (probe: insert 20–38 ms, save
     107–115 ms). That alone breaks the 150 ms target at 1k, and 10k would take about 1.5 s.
   - **Why only photos without keywords (a data-loss probe).**
     - The view model's context holds a tag with its `photos` loaded.
     - A background context saves 3 new photos linked to that tag.
     - The view model's context then inserts another photo with that tag and saves.
     - Result: the store keeps only the view model's links. The 3 background links are gone.
   - **So the rule is:** a background context may only insert rows with no relationships, and never changes an
     existing row. Photos with keywords are inserted in the view model's context, in chunks of 256 with a save and a
     `Task.yield()` between them.
   - **Where each rule is checked:** the rule by the unit tests above; the safety of the relationship-free inserts by
     `testPhotosAddedInBackgroundSurviveLaterEdits`.
4. **Missing files: rows the scan didn't find are `stat`ed** (off the main thread) and marked missing only when none of
   their files exists.
   - Step 4.6 says "photos under the scanned root that weren't discovered go into `missingPhotoIDs`", with no `stat`.
   - That would change what's visible today (`main` `stat`s every photo after each scan):
     - photos from an earlier library root would never be hidden, even when their files are gone;
     - photos under the root that the enumerator skips but whose files exist (inside a hidden folder, say) would
       disappear.
   - My version keeps today's result exactly, and after an unchanged rescan it `stat`s nothing.
   - `needsAvailabilityCheck` is gone from the scan path, as asked. Only `refreshAvailability()` sets it, and that
     keeps its semantics.
5. **The queued request stores the folder, not a flag** (`queuedScanURL`, latest wins). `handleFolderSelected` can
   request a different folder than the scan in progress.
6. **Progress** comes from a `@Sendable` callback per work item that hops to the main actor. There's no `AsyncStream`.
   The strings are:
   - "Scanning folder..."
   - "Reading metadata for N new photos... d/N"
   - "Adding N new photos..."
   - "Found X photos (Y new)", unchanged
7. **`Tag.parse` differs from the old inline split in one edge case**: a keyword that starts with `:` and contains
   another `:`.
   - `":a:b"` used to become category `a`, name `b`, because `split` drops empty pieces. That doesn't round-trip.
   - It now becomes one uncategorised name, `":a:b"`, and `fullName(parse(k)) == k` holds for every keyword.
   - Everything else parses as before.
   - Duplicate keywords in one file now link the tag once.
8. **New file `Library/ScanPlan.swift`**, which the task's Files list doesn't include. It keeps the diff pure and
   testable without a view model. No other task creates that name.
9. **`DiscoveredPhoto` has an explicit `init`**, since `key` is derived. It takes `metadata` with a default of nil, so
   the scanner's existing call compiles unchanged.
10. **Launch:** the main-actor target (≤ 150 ms) isn't met. `loadExistingData()` (Data Loading, task 10's region) stays
    on the main actor, as the task file allowed. See "Needs from other tasks".

## Decisions for the user

1. **A scan takes photos out of the bin when their files still exist.**
   - Existing behaviour, kept as the task file says: the old code set `isDeleted = false` on every photo it found.
   - Every launch runs a scan, so on `main` and on this branch **"Move to Bin" doesn't survive a relaunch** unless the
     file is also trashed.
   - Pinned by `testScanRestoresBinnedPhotoWhoseFileExists`.
   - Conservative option taken: kept. Changing it is small (`ScanPlan` stops emitting `restoresFromBin`).
     **Recommendation:** leave binned photos in the bin.
2. **Launch now shows photos whose files went missing since the last scan, until the launch rescan finishes.** That's
   about 0.7 s at 10k, and 0.1 s for 190 photos. This is what the task asked for ("trusting the last scan"), noted here
   because users can see it.

## Follow-ups

- **Sorting by EXIF `DateTimeOriginal` (proposal; not implemented, because it changes the visible order).**
  - `readMetadata` already opens each new file's properties during the scan, so reading
    `kCGImagePropertyExifDateTimeOriginal` (plus `OffsetTimeOriginal`) there is nearly free. That's task 23's
    `MetadataService`.
  - Store it as a new `PhotoAsset.captureDate`, a schema change (task 31's area), and sort by
    `captureDate ?? creationDate`.
  - Existing rows need a one-time background backfill, about 0.4 ms per file, spread across all cores.
  - File creation dates change when files are copied between disks, so capture time is the more stable order. The user
    should decide.
- **Today's behaviour when the library root changes.**
  - `handleFolderSelected` overwrites the single `PhotoLibrary`'s `rootFolderPath` and bookmark, then scans the new
    root.
  - Photos from the old root stay in the store and in the grid **as long as their files exist**. The scan `stat`s the
    rows it didn't find, which is the same result as `main`'s post-scan `stat` pass. They're hidden only when their
    files are gone.
  - They're never refreshed again (paths, sizes, bin), and no other scan finds them.
  - `PhotoAsset` has no relationship to a library, so scoping the grid to the current root would need one, or a
    `folderPath` prefix filter.
- **Unchanged-rescan wall time** is bounded by the background read of all rows (about 270 ms per 10k), which runs
  alongside the folder walk. Skipping the read when nothing was saved since the last scan, or caching the snapshot,
  could roughly halve `7w`. Both add invalidation risk, so I left them out.
- **The `7x` seed paths** could be made canonical in wave 3, re-baselining `7x`; `7w` already does this.
