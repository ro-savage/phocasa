## Deviations from the task file, and why

1. **RAW parameters are read in `EditSession.init`, synchronously, not in `begin()`.** The task allows the sidecar
   read to stay synchronous ("it's a small file"), and `main` reads it synchronously in `startEditing`.
   - I first loaded them asynchronously in `begin()`. A test then showed the gap. Until the load landed, the
     session held placeholder defaults: the sliders could show them for a frame, and a quick start/stop saved them
     over the saved edit. `testQuickRAWStartAndStopKeepsTheSavedEdit` failed with `("nil") is not equal to
     ("Optional(1.0)")`.
   - Reading in `init` removes the placeholder state entirely. The read goes through `RAWEditStore`, so it also sees
     a save that is still queued.
   - The detail view's per-navigation sidecar read, the one the task asked to move off the main thread, now runs on
     a background queue (`RAWEditStore.load`).
   - `begin()` warms the caches and starts the first render. It runs once, and later calls wait for that run, so
     tests can `await` it after the view model has started it.
2. **`RAWEditStore` is new, not in the task.** RAW saves are asynchronous now, and two things read the sidecar right
   after a save: the detail view's saved-edit render and a new session on the same photo. Without an overlay they
   would read the old file. The store keeps each save in memory until a `MetadataWriter.flush()` that started after
   the enqueue returns. The writer guarantees that flush sees every earlier enqueue.
3. **The "unedited image after saving" fix is a hand-off, not a view-side re-render.**
   - `end(save:)` returns a `SavedEditHandoff`: what was saved, plus the session's latest render and the parameters
     it shows. The view model publishes it as `savedEditHandoff`, cleared on navigation and when the detail view
     closes.
   - The detail view shows it at once. It then resolves the saved edit through `SavedEdit.render`, which reuses the
     session's image when it is a finished full-resolution render of exactly the winning edit. Otherwise it renders
     the edit on `.full`.
   - Until that resolves, `SavedEdit.interimImage` follows the same precedence as reopening the photo. A JPG edit
     wins over a RAW one. A render already on screen of exactly the winning edit is kept. When the winner isn't known
     yet, for example a JPG edit cleared and no RAW render seen, the unedited photo shows until the sidecar has been
     read.
4. **A session belongs to one photo.** The task said "`navigateDetail` saves the session before moving, as today".
   Today's version is the bug above.
   - Navigating now ends the session with a save, then starts a new one on the next photo, of the same kind.
   - If the next photo has no file of that kind (editing RAW, the next photo is JPG-only), edit mode ends. On `main`,
     the sidebar stayed open with nothing to render.
5. **Exports refresh what depends on the rewritten file.**
   - The view model's `exportRAWToJPG(replaceExisting:)` / `exportJPGPermanent()` keep their signatures for the
     views. They await the session's `Bool` exports, then:
     - call `photosDidChange([photo])` when the photo got a new JPG (task 10's request);
     - call `ImageLoader.shared.invalidate(path:)` for the written file (grid thumbnail);
     - bump `editedFilesVersion`. The detail view keys its load on it, clears `FullImageLoader`'s decodes and loads
       again.
   - After `exportJPGPermanent`, the session also clears the editing service's cache. Found by reading: on `main`,
     the reset parameters re-rendered the *cached, pre-export* source, so the view showed the unedited photo while
     the file had the edit baked in. `testExportJPGPermanentBakesTheEditAndClearsIt` covers the new behaviour; I
     didn't run it against `main`.
6. **`PhotoDetailView.renderSavedEdit` became `SavedEdit.render(jpg:raw:)`.** It is generic, so it can carry which edit
   it rendered. The four §D4 tests call it unchanged apart from the name, and one type annotation.
7. **The JPG comparison decodes at subsample 2**, or reuses a cached full-resolution decode. The session doesn't know
   the viewport, which is the task's "or 2 by default" case. Each side of the comparison is half the window wide, so
   a 16 MP JPG at subsample 2 (2456 px) covers a half-window on a 16" Retina display at fit.
8. **`EditViewModelBench` in `ImageEditingServiceTests.swift` was ported.** That file isn't in a wave-2 ownership row,
   but the helper used the removed view-model API and wouldn't compile. What it measures and its labels are
   unchanged.
9. **Test store handling.** `EditSessionTests` uses a temp-file SwiftData store per test, as the task asks.
   - Deleting a store while finishing tasks still held its objects made SQLite log "vnode unlinked while in use".
   - So each test's `tearDown` waits (up to 1 s) for its container to be released before deleting its folder. The
     tests also save the context after setting up model state, and autosave is off.
   - The final logs have no such lines, and no temp folders are left behind.
10. **Small interface differences from the task's sketch:**
    - `end(save:)` returns the hand-off (`@discardableResult`).
    - `EditSession.hasEnded` is readable.
    - `previewSize`, `previewDebounce` and `fullPassDelay` are static constants.
    - `canExport` no longer checks `isEditing`: a session exists only while editing.

## Decisions for the user

- **Navigating while editing keeps you in edit mode on the next photo.** It saves the photo you leave and starts
  editing the next one with its own saved parameters. This is the conservative reading of "saves before moving, as
  today": the sidebar stays open as before. It no longer carries the old photo's parameters and renders along, which
  was the bug. The alternative is to leave edit mode on navigation. When the next photo has no file of the kind being
  edited, edit mode ends.

## Follow-ups

- **Native-resolution rendering only when zoomed: a need observed.**
  - The 300 ms full pass renders the whole photo at native size after every slider pause (full lane; ~40 ms for
    24 MP JPEG, ~190 ms for a 16 MP RAW in task 13's numbers), even at fit.
  - At fit, it is also what makes a large Retina window sharp. The 1600×1100 preview is below a 16" window's
    3456 px.
  - So "only when zoomed" also needs a viewport-sized preview. Pass the viewport to the session and render the
    preview at that size, then render native size only when zoomed past it.
- **Metal preview.** The main-thread first draw of the full-resolution result is still ~26–28 ms (real 16 MP) and
  ~36 ms (24 MP) in the CPU-draw proxy. A Metal-backed view (`MTKView` + `CIRenderDestination`) would remove it, if
  it matters on screen.
- **Colour management.** No need observed here: output and its Device RGB tag are unchanged.
- **Saved-edit renders in the detail view are full resolution**, as since task 12: ~190 ms per RAW photo navigated
  to. They could render at fit size, then at full size on zoom.
- **The JPG comparison could pick its subsample from the viewport**, if the session is given it (see the first
  follow-up).
- **Memory:** after a save, the hand-off keeps the session's full-resolution render (up to ~92 MB for 24 MP) until
  the next navigation or until the detail view closes. When it is reused, it's the same object the detail view shows
  anyway, so no extra copy.

## How the coordinator's edit benchmark should drive the new API

`startEditing` and `stopEditing(save:)` are unchanged. Everything else goes through `vm.editSession`, which is a new
object per `startEditing`, so fetch it after each call. In `editTicks`:

```swift
vm.startEditing(photo: photo, isRAW: isRAW)                 // unchanged
let session = try XCTUnwrap(vm.editSession)                 // new: one session per startEditing
try await waitUntil { session.previewImage != nil }         // was vm.editedPreviewImage

// Full-resolution result: nil after every change, set when the 300 ms .full pass lands.
```
