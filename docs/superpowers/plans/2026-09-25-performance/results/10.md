**Branch:** `perf/10-library-data-path` · **Status:** complete. Every acceptance target is met in Debug at 10k photos
(medians of 5), under load from other agents. The coordinator should re-measure on a quiet machine.

Filter clicks, sort toggles and search keystrokes now take 1–17 ms, down from 340–530 ms. Ratings and bin moves take
7–9 ms, down from 70–380 ms, and are now bounded by SwiftData's `save()` itself (7–9 ms), which this task doesn't
change.

## Deviations from the task file, and why

1. **More incremental than the task file planned.** I first built the plan as written: fetch once, re-filter the facts
   and recount on every change. That already cut filter clicks to 7–15 ms. But `setRating` stayed at 17–19 ms, bin
   moves at 21 ms, and search at 19.5 ms, because every call still ran three or four O(n) passes. Each pass costs
   3–8 ms in Debug (dictionary hashing, `elementsEqual`, index rebuild), on top of the roughly 8 ms save. The probe
   numbers are above. So:
   - **Counts** are cached per filter set. Search never recounts, since counts ignore search. Mutations update the
     counts in O(1) per photo (`PhotoQuery.updateFacetCounts`), with a full recount above 1,000 photos.
   - **The grid.** `GridState` records how `photos` was built: the query, which list, that list's version, and the
     shown positions. A refresh that changes nothing does nothing. Mutations of up to 8 photos patch `photos` in place
     (binary search and array insert/remove, about 1–10 µs). Larger ones re-filter once.
   - **`index(of:)`** is backed by a lazily rebuilt `[UUID: Int]`. It calls `access(keyPath: \.photos)`, so views
     that read it still update.
   - **Finding a photo** is O(1) through the grid when the photo is shown. Otherwise it's a buffer-pointer scan that
     reads only ids, smaller list first.
   - `photos` and the count properties are **assigned only when they change**, so the grid and sidebar aren't
     invalidated for nothing.

   Correctness is checked against a full reload after every step, by both oracle tests.
2. **Search fast path.** When the lowercased needle and a search key are both ASCII without `\r`, matching uses
   `memmem`. In that case each byte is one `Character` and no two spellings are canonically equivalent, so the result
   is exactly what `String.contains` returns. Other keys still use `String.contains`. A 2,000-case randomised test
   checks the equivalence. Search went from 10.7–12 ms to about 4.3 ms per 10k keys.
3. **Extra `Library` API** beyond the task's interface. All the specified names and signatures exist unchanged. The
   additions:
   - `PhotoFacts.init(_:tags:)` with a `TagFactsCache`, keyed by object identity and retaining its tags. It halves the
     cost of building facts (126 → 66 ms at 10k).
   - `TagFacts`, `PhotoQuery.matchesEverything`, `matchingIndices(in:)` and `updateFacetCounts(_:replacing:with:)`.
4. **`loadExistingData()` now always applies the active filters and search.** Before, it reset `photos` to the
   unfiltered list while the sidebar still showed the filters as active. That happened after scans, bin moves,
   permanent and file-type deletes, and `refreshAvailability()`. This is a bug fix, and follows from the task's design
   (`loadExistingData` ends in `refreshVisiblePhotos()`). Covered by `testLoadExistingDataKeepsActiveFiltersAndSearch`
   and `testMoveToBinKeepsActiveFilter`.
5. **Clicking Bin applies the current search text.** The task allowed this; noted here as asked.
6. **`tagCategories` is re-sorted when category membership changes** (loads, tag add/remove, bin moves), by the
   unfiltered library counts. Before, a new category was appended at the end, and the list was re-sorted by the next
   click's reload. The sort key itself is the same as before (count descending, then name).
7. **In-memory tag inserts sort with the fetch's own `SortDescriptor`s** (`.localizedStandard` for strings). The old
   `refreshTagLists` used Swift `<`, which could disagree with the fetched order, for example on case.
8. **`tagsByCategory` doesn't exclude tags with a `parent`.** The old sidebar filter did (`$0.parent == nil`).
   Nothing ever sets `parent` (§H4), so nothing changes in practice. The `tag.children` rows are left in place, as the
   task asks.
9. **Edge cases that differ from before.**
   - `.tagCategory("")` now matches nothing, because `tagCategories` holds only non-empty categories. Before, it
     matched photos with uncategorised tags. The UI never creates this filter.
   - Search text containing `\n` never matches. The search field is single-line.
   - `SidebarFilter.bin.matches` returns `true` (it's a special filter). Before, it read `isDeleted`, but that code was
     never reached.
10. **`selectedPhotosList` stays where it was**, next to `canExport`. Only its body changed, which keeps the diff away
    from task 13's properties.
11. **`moveToBin` / `restoreFromBin` remove the moved photos from `selectedPhotos` in one `subtract`** instead of once
    per photo. The final state is the same, with fewer observation notifications.
12. **Found while testing: reading `photo.isDeleted` after a `save()` returns `false`.** This happens even though the
    store holds `true`: a fetch returns the photo, and after that fetch the property reads `true` again. My guess is
    that the KVC key `isDeleted` collides with Core Data's own `NSManagedObject.isDeleted` (spec §H5). The old code
    hid this by re-fetching after every save.
    - No app code reads `isDeleted`. Bin membership now lives in `binPhotos`.
    - The store is correct: I checked delete/restore cycles with no fetch in between, reading through a separate
      context.
    - My tests check the bin through a separate context (`storedBinIDs()`) instead of reading the property.
13. **New `photosDidChange(_:)` hook** for model changes made outside the view model. See "Needs from other tasks".
14. **`emptyBin()` keeps its "no context → do nothing" guard** (`modelContext != nil`), with no fetch.

## Follow-ups

- **Mutations now cost about one `save()`**: 7–9 ms at 10k on an on-disk store, and about 15 ms for 50 rows. Going
  lower means coalescing saves (autosave), which changes durability, so I didn't do it.
- **`3f` (tag filter change, about 16.5 ms in Debug).** Most of it is `Set<UUID>` hashing, which isn't specialised in
  Debug. `matchingIndices` and `facetCounts` each evaluate the tag group for every photo. One combined pass, or tag
  ids interned to small integers, would roughly halve it.
- **Building facts in `loadExistingData` costs about 66 ms of model reads at 10k.** It could move off the main actor
  together with task 20's scan work.
- **I didn't measure Release builds.** The remaining pure-Swift passes (count, filter, index) should be several times
  faster there.
