**Read the last row with the one above it.**
- On `main`, the full render "returns" in 13.8 ms because its pixels are deferred. The real render then runs inside
  the first draw, on the main thread.
- On the branch, the pixels are produced on the full lane (40.6 ms, off the main thread).
- The first draw now pays only CoreGraphics' own resampling (~35 ms for 24 MP into 1600×1067 in this CPU-draw proxy).
- End to end (render + draw), `main` takes 84.9 ms and the branch 76.0 ms. The main thread's share drops from 71.1 ms
  to 35.4 ms.

This increase is the intended effect of spec §E3, not a regression.

## Deviations from the task file

1. **`lane:` defaults to `nil` (auto), not `.preview`.** `nil` sends sized renders to `.preview` and full-resolution
   ones to `.full`. `PhotoDetailView` (saved-edit renders) and `loadJPGComparisonImage` call full-resolution renders
   without `lane:`. With a `.preview` default, those renders would block edit previews, which breaks the invariant
   in `Lane`'s own doc comment. Call sites are unchanged, and the view model passes lanes explicitly anyway.
2. **The output colour space is tagged Device RGB, not sRGB.**
   - I checked the task's suggested `colorSpace: sRGB` against today's `createCGImage(_:from:)`.
   - The bytes match, but today's image is **tagged `kCGColorSpaceDeviceRGB`**, whatever the header says.
   - An sRGB tag would change downstream colour matching, and it changed exported JPEG files.
   - `format: .RGBA8, colorSpace: CGColorSpaceCreateDeviceRGB(), deferred: false` keeps the tag, and its pixels are
     within ≤ 1.
   - The tests now also assert the tag.
3. **Exports stay deferred** (`createCGImage(_:from:)`, unchanged).
   - The encoder pulls the pixels on the full lane, so nothing reaches the main thread.
   - The files stay byte-identical: checked at q 0.95 and 1.0.
   - With a non-deferred sRGB image, the export differed by up to 4 levels after re-decoding.
4. **The standard (JPEG) source is shared by both lanes, not cached per lane.**
   - It is an immutable, `Sendable` `CIImage`, so one decode serves both lanes. Per-lane copies would decode twice and
     hold a second 24 MP bitmap.
   - `CIRAWFilter` isn't thread-safe, so it stays per lane.
   - `prepareStandard` loads once, and `prepareRAW` warms both lanes in parallel.
5. **`clearCache()` is `nonisolated` and uses a cache generation.**
   - It bumps a lock-protected generation, drops the shared source, and asks the lanes to drop their RAW filters.
   - Any render that starts after it returns sees a clean cache, which keeps the serial-queue ordering the old code
     had.
   - One small fix came with it: the old `prepareStandard` recorded the URL even when loading failed, so a later render
     could reuse the previous photo's image.
6. **Export test at quality 1.0.**
   - Full renders are bit-identical across contexts, but a JPEG encode at 0.95 isn't reproducible. The first
     render/encode in a process differed from later ones by up to 6 levels on identical input.
   - At 1.0, the files were byte-identical.
   - `quality` is passed straight through to ImageIO.
7. **Tests 6–8 were written with their implementation, not before the refactor.** They need `rawScaleFactor`, `lane:`
   and `renderCount`, which didn't exist yet. Pre-refactor versions of 7 and 8 were run against the old service and
   failed (TDD evidence above).
8. **The parameter sets are a superset of the task's list:** "brightness −25" and "rotation −7 + flip vertical" were
   added. The full-render test uses 4 sets (default, combined, clarity −50, rotation 10).
9. **Small additions for tests and edge cases.**
   - Internal `init()` (tests use private instances) and `nonisolated var renderCount`.
   - `rawScaleFactor` gets the **oriented** native size, because `CIRAWFilter.nativeSize` ignores orientation.
   - The post-decode `scaleToFit` still runs if the output exceeds `maxSize` by more than 1 px.
10. **Exports are never stale-skipped.** A user-requested file write shouldn't silently vanish, and nothing cancels
    exports today.
11. **Full lane QoS is `.userInitiated`, preview `.userInteractive`.** The old single queue ran everything at
    `.userInteractive`.

## Follow-ups

- **The CPU-draw proxy still costs ~28–40 ms.** With the pixels ready, the remaining "first draw" is CoreGraphics
  resampling 16–24 MP on the CPU. SwiftUI/Core Animation compositing on screen is a different path. A screen-sized
  representation or a Metal-backed view (`MTKView` + `CIRenderDestination`) could remove the rest, if needed after
  waves 1–2.
- **Aborting the in-flight full pass on a new tick** needs cancellable rendering that stays pixel-identical. Banding
  wasn't (max diff 3). With two lanes, the contention it would remove is small (RAW tick during 39.9 vs idle
  35.0 ms).
- **Colour management** (Device RGB working space and output tag): a separate, deliberate change, because it changes
  output.
