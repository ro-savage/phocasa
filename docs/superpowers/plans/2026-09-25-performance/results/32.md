### How launch works now

1. `open(_:)` counts the photo rows (0.3 ms). At 500 or fewer it loads synchronously, exactly as before, and every
   existing test takes this path. A small library costs at most about a frame to load synchronously (~33 µs a photo).
2. For a bigger library it fetches the `PhotoLibrary` row, so a rescan requested now can queue. It starts the scan
   queue with the background load first (`isScanning` is true and `scanProgress` is "Loading library..."), queues the
   launch rescan, and starts that rescan's folder walk at once.
3. **Off the main actor:** `LibrarySnapshot.read` runs one ordered fetch per list through `sort.fetch`, and two unordered
   halves of the rows give the facts and the stored rows. At 10k on a fresh container it takes 272–286 ms, against
   381–397 ms for one context doing it all.
4. **On the main actor, meanwhile:** unordered pages of 400 rows are fetched as models of the main context and held
   (10–14 ms a turn, yielding between them), then the tags get a turn of their own (~9 ms). Once the snapshot is in,
   `model(for:)` looks the rows up in snapshot order, 5,000 per turn. The rows are registered and filled in by then.
5. **One turn:** lists, facts, counts (from the snapshot), tag lists and the grid, so no main-actor turn ever sees a
   half-built library. A sort toggled during the load is applied with `LibrarySort.reorderAfterToggle`. Filters and
   search set during the load are applied by `refreshVisiblePhotos`. If a full `loadExistingData()` ran since
   `open` (a newer load), the background one is dropped.
6. The launch rescan follows at once. It uses the walk started at launch and the snapshot's stored rows, unless:
   - another scan was requested meanwhile;
   - a load ran since;
   - the context had unsaved changes.
   
   It usually has nothing to do, so it ends ~50 ms after the grid appears.
7. `waitForScans()` returns after the background load (applied or dropped), the launch rescan and any queued scan. That
   is task 33's contract, tested.

### How a scan updates the library now

- The plan's updates are written as before. `photosDidChange` still covers the case where only paths or sizes
  changed.
- New rows are then brought into memory:
  - photos inserted on the main context are used as they are;
  - photos inserted in the background, and library photos whose files are back, are fetched by id on the main context,
    500 per turn.
- `updateLibrary(adding:facts:removing:)` adds them, and removes the photos that went missing. That is O(k log n) for up
  to 8 photos (patching the lists, grid and counts); above that, one merge (`sort.merge`) and a recount. New tags
  refresh the tag lists from one small fetch.
- If a full load ran during the scan (its awaits, or a hook), the scan reloads instead, so no photo is added twice
  (tested).

## Deviations from the task file, and why

1. **The 7v main-actor target (≤ 150 ms total) is missed: ~300 ms, in turns of ≤ 13 ms.** Step 3's suggested approach
   was a background snapshot, then `context.model(for:)` for cheap models. It measures 30 ms, but those models are
   faults, and the grid's `ForEach(photos, id: \.id)` reads every photo's `id` at once: 1.6 s, one query per row. So
   the main context must hold filled-in rows, and that costs ≥ ~215 ms at 10k whichever fetch is used (table above).
   What the task could still get is launch never blocking the main actor: the synchronous part is 0.6 ms (step 2's
   stop condition, "well below 350 ms", is met), and no turn exceeds ~13 ms. The way to ≤ 150 ms is under follow-ups:
   a grid that doesn't read models for identity. It needs `PhotoGridView`, outside this task.
2. **The snapshot is read in parallel** (ordered fetch plus two unordered halves). With one reader, the library
   appeared ~80 ms later than today (a new line, "COLD until loaded", +18–23%), although nothing froze. With the split
   it appears 7% sooner than today, and the launch rescan ends 45% sooner. The price is ~40 ms more main-actor time in
   total. The one-reader version is commit `4f44e23` if the coordinator prefers the lower total; it's
   `LibrarySnapshot.read` alone.
3. **Small stores still load synchronously** (`backgroundLoadThreshold` = 500 photos, about a frame of work). It keeps
   every existing test on today's exact path, and a small library never flashes "Loading library...". Tests reach the
   background path by lowering the threshold, and `pageSize` for several turns.
4. **The launch rescan reads ahead.** The task file doesn't ask for this. Without it, `7v` until the rescan ends would
   have regressed: load ~430 ms plus the rescan's own ~330 ms read, against 705 ms. Its folder walk starts at `open`,
   and it takes the stored rows from the snapshot. Both are dropped if another scan is requested. The rows are also
   dropped if a load ran since or the context has unsaved changes (tested). Nothing can change photo rows before the
   library is shown, and the rescan starts in the same turn as the apply.
5. **The bin fix needed no `isDeleted` workaround.** `applyScanUpdates` fetches each row right before writing it, and
   the store keeps the bin flag through the write. `testBinnedPhotoWhoseFilesChangedStaysInTheBinWithNewPaths` checks
   that through a separate context. `ScanPlan.Update` loses `restoresFromBin` and gains nothing.
6. **`LibrarySnapshot` duplicates `PhotoFacts(_:tags:)`'s construction off the main actor.** `PhotoFacts.init(_:tags:)`,
   `TagFacts.init` and `TagFactsCache` are `@MainActor`, and `PhotoQuery.swift` isn't mine.
   `testSnapshotReadsWhatAFullLoadBuilds` pins the equivalence (see Needs).
7. **The deletes' in-memory removal lives in `+ListEditing`** (`updateLibrary`, `fileTypeDeleteDidFinish`), as the
   coordinator notes allow. In `deletePermanently` the call sits just before the `context.delete` loop, not where
   `loadExistingData()` was after the save: it reads each photo's id, which mustn't be read after the delete.
8. **Delete and launch tests are in `ScanTests`**, the test file I own, next to the oracle helper.
9. **Harness:**
   - `waitForScans()` was added after the warm `setModelContext` in the suite, before `refreshAvailability()`. Without
     it the background load of the 10k seed would overlap the warm lines. On `main` it returns at once.
   - `COLD setModelContext` keeps its label; for a big library it now measures only the synchronous part, and its
     `allPhotos=` shows 0. The new "until the library is loaded" line gives the wall time to the grid.
10. **`insertInBackground` returns `[UUID]`, and `insertScannedPhotos` returns `(photos, createdTags)`.** The scan
    needs them to bring the rows into memory. Each keeps its single `PhotoAsset(` creation site (Needs → task 33).

  - Move to Bin → quit → relaunch: still in the bin, for a small and a big library;
  - Empty Bin and a RAW-filter delete on a big library: no hitch afterwards.

## Follow-ups

- **Launch to ≤ 150 ms of main-actor time.** Let the grid take photo identity from `library.shownIDs`, not the models.
  The launch could then leave rows as faults: `model(for:)` ×10k is ~30 ms against ~250 ms of page fetches. A visible
  cell's photo then fills in when shown, ~0.18 ms each (both measured). That needs `PhotoGridView` (its `ForEach` and
  `.id(photo.id)`), and a check that nothing else reads every model at once. Selection and counts already use facts.
- **`7u`: raise the patch limit for inserts.** 10 new photos exceed `patchLimit` (8), so `7u` takes the merge path and
  its full recount (~9 of its ~20 ms). A higher limit for inserts would halve it.
- **`loadExistingData()` is still one ~330 ms block when it runs.** It now runs only from `refreshAvailability()`, a
  load that overtook a scan, and whatever task 33's backfill uses to re-sort. A chunked variant, like the background
  load, would suit the backfill.
- **The tag fetch costs ~9 ms for 40 tags**, even warm. Worth a look (the `.localizedStandard` sort?).
- **The harness's model-read baselines (`6a`–`6i`)** were +1.5–7% on the branch across three A/Bs, with no difference
  in-process (above). If the quiet re-run shows it too, look at process state after the background load.

## Couldn't verify

- **The running app** (the rules forbid launching it). The UI during the load is inferred from the run-loop probe and
  the no-half-built-state test, not seen on screen.
- **Quiet-machine numbers:** every run overlapped other agents (load 2.2–7.4).
- **macOS 14:** concurrent reads through several `ModelContext`s on one container, and `fetchOffset` paging without a
  sort, were measured on this machine's macOS 27 only. Correctness doesn't depend on either: a row the pages miss

- **Real photos:** `~/PhocasaBenchRAW` wasn't needed. The metadata path is unchanged, and the tests use generated
  JPEGs and fake RAW files in temp folders.

  set.
