## Deviations from the task file, and why

1. **The scroll-wheel flip uses the window frame's height, not `contentView.bounds.height`.** The hosted-window
   test showed SwiftUI's `.global` space starts at the top of the window *frame*, title bar included. For a titled
   window without a full-size content view, flipping with the content height put the viewport 32 pt (the title
   bar) too low: `.global` y=107 against a true top-left y of 75, and the test failed. Flipping with
   `window.frame.height` is right for both window styles; they agree when the content view is full-size. As a
   result, the parameter is `windowHeight`. I added an overload that also checks window identity, so "another
   window" is unit-tested too.
2. **`ZoomPanState` is created by the container**, as `@State`, and passed to `ZoomableImageView` and `MinimapView`.
   The container never reads its properties: it only creates it and calls `reset()` on navigation. The counters
   confirm zoom frames re-run neither the container nor the overlay. The reasons:
   - zoom survives switching to a comparison view and back, as it did before;
   - the minimap stays drawn above the overlay controls, as it did before. It overlaps the left chevron, so moving
     it inside `ZoomableImageView`, below the controls, would change which one receives the click.
   `grep` confirms nothing else references it.
3. **Thumbnail placeholder dropped (step 7.1).** It can't arrive first:
   - The 400 px thumbnail costs as much as or more than the fit decode it would stand in for. Real JPG: 27.9 ms
     against 29.8 ms (16.5 ms for subsample 2). 24 MP JPG: ~94 ms (software path) against 48–59 ms. ARW with
     today's `Always`: 100 ms against a 15 ms embedded preview.
   - It never hits `ImageLoader`'s cache: the grid requests `max(300, cell × scale)`, bucketed to ≥ 500, while the
     detail view asks for 400.
   - With prefetch, navigation is a cache hit anyway.
   The minimap thumbnail is still loaded after the fit image, as before. Because of this, no cache-only
   `ImageLoader` lookup is needed.
4. **The loader API has additions beyond the task's interface.** Everything the task listed is kept:
   `load(path:subsample:)`, `cachedImage`, `prefetch(paths:subsample:)`, `subsampleFactor`. The additions:
   - `loadFit` / `cachedFit` / `prefetchFit(paths:viewportPixelSize:)` choose the variant per image. A single
     subsample for all neighbours is wrong when they differ in orientation, since a portrait photo needs a
     different factor, and for RAW files, which take the preview.
   - Also `info(path:)` / `cachedInfo`, `clear()`, `init(byteLimit:)`, `cachedBytes`, `decodeCount`.
   - The cache key is (path, variant), where the variant is `subsample(n)` or `rawPreview(maxPixelSize)`.
   - A cached decode with more pixels serves a fit request: after zooming, or after a first load made before the
     viewport size was known.
5. **Extra loader behaviour, not in the task:**
   - Loads of a key in flight join it, rather than decoding twice.
   - A foreground load whose callers were all cancelled skips the decode, so key repeat doesn't queue a backlog.
   - Joining a prefetch raises its QoS. This is defensive: interleaved A/B runs at load 3–5 showed no difference
     (p90 0.0–0.1 ms both ways). The one run without it at load 7–9 had p90 44.5 / 131.6 ms. I didn't add artificial
     load to prove it, since that would skew the other agents' runs.
6. **RAW full decodes are forced off the main thread into 8-bit bitmaps.** ImageIO defers RAW decoding:
   `CreateImageAtIndex` returns in 2.5 ms, and the 190–212 ms decode then lands on the main thread at first draw.
   An 8-bit P3 bitmap is 61 MB instead of 122 MB at 16 bpc.
7. **Full resolution loads whenever the image is drawn with more device pixels than it has.** That covers zooming,
   the viewport growing (for example the edit sidebar closing), and a RAW preview at fit. On a Retina full window,
   the 1616 px preview is short of pixels at fit, so a RAW-only photo shows the preview at once and the sharp
   decode about 236 ms later, in the background. It only applies when the loader's image is on screen, never an
   edit render. The double-click "1:1" target uses the photo's full pixel size (`sourcePixelSize`), as before.
8. **§D4 got a testable helper and tests** (`PhotoDetailView.renderSavedEdit`), not only code inspection. The RAW
   sidecar read now runs only when the RAW render is needed.
9. **Small behaviour changes that go with the new loading:**
   - A load that finishes after a newer navigation no longer overwrites the newer photo. This was a race before.
   - The previous photo's saved-edit render no longer stays on screen under the next photo while the next photo's
     render runs.
   - The fit also follows aspect-ratio changes between photos. Before, `fitSize` updated only on a resize, which
     would have been wrong once portrait photos show as portrait.
   - Closing the detail view empties the loader's cache (up to 512 MB), so the memory is released as before.
     Reopening is then a cold decode, as before.
10. **`ZoomableImageView` and `DetailOverlayControls` are identity-`Equatable`.** They use `@preconcurrency Equatable`,
    because `View` is `@MainActor` and SwiftUI compares views on the main actor. Without this, closure properties
    made them re-run on every slider tick; the counters show 60 → 0.
11. **`MinimapView` takes a `DisplayImage`.** The 400 px thumbnail `NSImage` is wrapped as `.up`.
12. **Extra test file `DetailViewTests.swift`** for the scroll, §D4, view-geometry and hosted-window tests.
13. **Fixes-only fallback branch** (`perf/12-detail-view-fixes`). It isn't in the task file; see the top of this file.

## Follow-ups

- **RAW-only navigation** still does a ~236 ms full decode in the background per photo on Retina, because the
  preview is smaller than the window. Options: prefetch the full decode for +1 (CPU and 61 MB each), or decode at
  viewport size with `CIRAWFilter.scaleFactor` (~28 ms at 1600 px in imagebench).
- **Memory while in the detail view:** up to 512 MB of decoded photos, about 5 at 24 MP subsample 1 and 8 at
  16 MP. It's released on close. A lower limit would still cover ±1/+2 prefetch (4 photos).
- **A cold jump** (for example the first photo opened) still costs one fit decode, 30–80 ms. If that ever matters,
  the 160 px EXIF thumbnail (`IfAbsent`, 0.4 ms) could serve as a placeholder.
- The hardware JPEG decoder is shared with task 11's thumbnail decodes at 751–1500 px. A detail decode can wait
  behind grid work; nothing measured this.
