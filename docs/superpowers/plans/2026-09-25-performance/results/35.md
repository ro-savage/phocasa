## Deviations from the task file, and why

1. **`SavedEditState` (new type).** The detail view's saved-edit logic moved from five `@State` properties into an
   `@Observable` class in `Editing/SavedEdit.swift`.
   - It has to decide more now: the fit render, the native upgrade on zoom, a larger render on a grown viewport,
     hand-off adoption, and the prefetch.
   - The step-3 test "a saved edit is shown at viewport size on navigation, and at native size after zoom" needs
     something observable.
   - `PhotoDetailView.init` gains defaulted `zoom:` and `savedEdit:` parameters, so a hosted test can zoom and
     observe. The container still creates both itself in the app.
2. **The next photo's saved edit is prefetched (not in the task).** The prototype showed that a fitted render alone
   cuts a RAW's time-to-show by only ~12%: its decode, not its size, dominates.
   - At fit size, one render ahead costs ≤ 26 MB. So after resolving the photo's own saved edit, the view renders the
     next photo's in the direction of travel, if the model says it has one (a JPG edit or `hasRawEdits`).
   - Navigating there shows it at once: 0.8 ms at 250 ms per photo. At key-repeat speed it joins the render in
     flight: 101 ms instead of 188 ms.
   - A prefetched render is shown only if it is still the photo's winning saved edit (JPG parameters from the model,
     the RAW sidecar through `RAWEditStore`) and covers the current viewport. Otherwise the edit renders again.
   - It doesn't run while editing (the session's passes use the same lane). Prefetches are dropped on close and after
     exports.
   - **Peak memory in the detail view:** the photo's render plus one ahead, ≤ 52 MB, against 61–92 MB for one native
     render on `main`.
   - It is self-contained (`3d8f270`) and can be reverted alone if the coordinator prefers.
3. **The JPG comparison's saved JPG edit is fitted to half the viewport.** It was native. It is small and in my files:
   61 MB → ~20 MB, 40 ms → ~10 ms. The unedited JPG decode (subsample 2) is unchanged.
4. **Fitted RAW passes use draft mode,** because that is what the service does for any sized render. The pixel rule is
   "the service's output for that size", and changing `ImageEditingService` was out of bounds. The sharpness check
   above found no softening at these scales.
5. **The look at fit changes slightly.** Sharpness (1.5 px), clarity (20 px) and noise reduction act in the render's
   pixels, so a fitted pass shows them at display scale.
   - The native pass downsampled for display shows them smaller. The table above measures the gap.
   - Today's preview, which the user sees before every pass, differs about twice as much.
   - Zooming in (native) and exports look as before. **Coordinator:** check by eye that an edit with clarity at fit
     looks like the zoomed-in edit.
6. **Task-file figures, checked:**
   - "~190 ms per 16 MP RAW" pass: the warm pass after a pause is 95–115 ms through the session (67–75 ms for the
     service call). 190 ms is the fresh-filter render, the navigation case.
   - "The 300 ms full pass" is the 300 ms pause before the pass.
   - "~40 ms for 24 MP JPEG" is right: 40–43 ms.
7. **After a save, one render more than `main`.** When the sidebar closes, the detail view widens from 2894 to 3456 px,
   so the session's pass no longer covers it. The saved edit re-renders at the new size: RAW ~40–60 ms warm, off the
   main thread, with the session's pass shown meanwhile (no flash). `main` reused its native render. Memory is still
   lower: 47 MB against 61 / 92 MB.
8. **`fullImage` keeps its name,** for the harness and the view. It now means "the pass": fitted, or native
   (`fullImageIsNative`).
9. **A fitted render's 1:1 double-click target is the edit's native size** (`fullImageNativePixelSize` /
   `SavedEditRender.nativePixelSize`), so double-click still zooms to 1:1, not to 2×.
10. **The view model is unchanged.** The viewport reaches the session from `PhotoDetailView`, as the coordinator notes
    suggested. `MainContentView` is unchanged too.
11. **`prefetchNeighbours` (the loader's prefetch, task 12's code in my file) now returns the next photo,** for the
    saved-edit prefetch. What it prefetches is unchanged.
