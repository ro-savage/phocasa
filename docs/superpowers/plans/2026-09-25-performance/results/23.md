## JPEG rating writes dropping camera metadata (from task 21)

**Confirmed.** It happens on `main` (`0da2f79`) and on the pre-wave-1 code (`feed379`), with identical output (4,192,255 B). The mechanism, `CGImageDestinationCopyImageSource` with `kCGImageDestinationMergeMetadata`, dates from the first commits. ImageIO rebuilds the Exif APP1 from its own model and drops what it doesn't model.

Generated files add to that picture:
- `main`'s path also **drops COM segments and unknown APPn segments** (a test APP9).
- It keeps an ICC APP2 profile.
- It rewrites an IPTC-IIM APP13 with the new keywords, keeping other IIM data such as a caption. A file without APP13 gets none; ImageIO then reports the IPTC keywords derived from XMP.

**Fix** (`6c662b8`, inside `MetadataService`):
- **How it writes.** ImageIO's rewrite is still made exactly as before, but only as the generator of the metadata. Its XMP APP1 segment and its APP13 IPTC-IIM segment (if any) are spliced into the original bytes, and everything else stays byte-identical. The rating, `dc:subject` and IPTC keywords are therefore exactly what they are today, and so is their syncing.
- **Where the segments go.** The new XMP goes where the old one was, or after the JFIF and Exif segments; APP13 goes where it was, or right after the XMP.
- **MPF.** Nothing may change after an MPF segment, because its image offsets count from its header. Every change lands before it, so the preview stays reachable.
- **Fallbacks.** In these cases the splice returns nil, the write keeps ImageIO's output (today's behaviour) and still succeeds:
  - fill bytes or standalone markers in the header, or a truncated segment;
  - extended XMP;
  - more than one XMP or IPTC segment;
  - IPTC in the original but none in the rewrite;
  - an XMP or IPTC segment after the MPF one;
  - a spliced file that doesn't read back through ImageIO with the new rating and keywords.
- **Unchanged.** The write is still atomic (temp file and `replaceItemAt`), and file dates, symlinks and read-only handling are as before.

## Deviations from the task file, and why

1. **C: click count instead of a time window, and a deferred clear.**
   - The task file offered either `clickCount ≥ 2` or a time window. I first built the time window (7b761ba).
   - Self-review found a real hazard in it. In a rating filter (Unrated, 3 stars, …) the first click rates the photo, and it leaves the grid at once. The next photo's cell takes its place, so the second click lands on *that photo's* stars. It has fresh `@State`, so it got rated too. The user double-clicks stars, so an Unrated triage pass would rate two photos.
   - `RatingView` now ignores any click with `NSEvent.clickCount` ≥ 2, wherever it lands. That is the window server's own double-click detection, time and distance both.
   - SwiftUI runs the tap action synchronously while AppKit dispatches the mouse-up (probed), so `NSApp.currentEvent` is that event. SwiftUI's tap gestures don't expose the click count, just as they don't expose modifiers (`NSEvent.modifierFlags`, a known exception).
   - A click on the *current* star clears after `NSEvent.doubleClickInterval` unless a second click follows. A double-click on the current star therefore changes nothing: no 3 → 0 → 3, and the photo doesn't drop out of a filter. See Decisions 1.
2. **C: the stars are an overlay outside the cell's gestures.** I probed ten gesture wirings. No gesture on the rating row alone gives both an instant click and a double-click that doesn't open. The cell's simultaneous double-tap fires for a double-click anywhere inside the cell, and the instant row-only wirings all still opened the photo. With the overlay:
   - a star click doesn't select (as before);
   - a thumbnail click still selects at once, and a thumbnail double-click still opens;
   - the hidden placeholder keeps the layout identical.
3. **C: the click-test harness changed.**
   - The panel is now borderless and non-activating, so it receives synthesized clicks without being key. The old titled panel couldn't become key while the screen was locked, and every click test *skipped*; probed, a borderless panel gives the same gesture results.
   - Events go through `NSApp.postEvent` and then `nextEvent`/`sendEvent`, so `NSApp.currentEvent` is set, as it is for real clicks. With `window.sendEvent` it is `nil` (the pitfall the coordinator flagged; probed).
   - `testDoubleClickOnTheStarsOpensWithoutRating` is replaced, as the coordinator said.
4. **A: the modification date of sidecars advances.** The task file said to restore file dates "as the image path does". Sidecar writes never restored dates before (`String.write(atomically:)`), and Lightroom and Bridge use the sidecar's modification date to notice external metadata changes. The creation date, permissions and xattrs are kept (`replaceItemAt`).
5. **A: what counts as unparseable.**
   - It is any existing sidecar that isn't well-formed XML, or that ImageIO can't read as an XMP packet, empty files and UTF-16 included.
   - ImageIO's parser is lenient: it accepted mismatched tags and dropped content (probed). So well-formedness is checked with `XMLParser` before an update.
   - The skip is visible through the `updateSidecar` result, as are read-only files, unchanged values and failures.
6. **A: a write that changes nothing doesn't touch the file,** so rating a Lightroom sidecar with the same value doesn't reformat it.
7. **A: edit writes touch only `phocasa:EditParameters`** (the coordinator's note).
   - `writeEditParameters` and `clearEditParameters` no longer read a rating. They no longer copy `readMetadata`'s values, which include ratings embedded in the RAW, into the sidecar.
   - With no sidecar, an edit write creates one holding only the edits, and a clear creates nothing.
8. **A: read-only sidecars are skipped** (the old atomic write replaced them), and symlinked sidecars are written through (the old write replaced the link). This matches task 14's rules for images.
9. **A: reads go through ImageIO,** with a text fallback that accepts both forms for text that isn't a packet. Two bug fixes come with it:
   - keywords now come only from `dc:subject` (tone-curve points and `lr:hierarchicalSubject` used to become tags);
   - XML entities are decoded (the old reader returned `a &amp; b`, and each rewrite escaped it again).

   `parseXMPSidecar(_:)` and `parseEditParameters(from:)` keep their signatures, and every existing `MetadataParsingTests` test passes unchanged.
10. **A: a namespace-prefix conflict.** A sidecar that binds Phocasa's namespace to another prefix can't be registered as `phocasa`, so the edit write returns `.failed` and leaves the file untouched. A rating write still works.
11. **A: edits in sidecars are compared by value and written with sorted JSON keys.** `JSONEncoder`'s key order varies: 6 different encodings of one `EditParameters` in one process (probed). So "unchanged" once came back as `.written`. `testSameEditsEncodedDifferentlyCountAsUnchanged` was red before the fix.
12. **B: how I read "keywords travel with the rating".** Every rating *or* tag change on a pair writes the photo's whole current state, its rating and *all* its keywords, to both the JPG and the RAW's sidecar. The two files never disagree, and the sidecar's keywords never go stale next to a new rating.
    - The sidecar write goes through A, so saved RAW edits and other apps' XMP are kept.
    - Callers are unchanged, and `MetadataWriteItem(path:rating:keywords:)` still compiles.
    - The writer turns one item into two paths, each coalesced and ordered on its own. The sidecar write stays serialised with that RAW's edit writes, because they share the path.
13. **The JPEG splice** is outside the task file; the coordinator requested it mid-task.

## Decisions for the user

1. **Clearing a rating by clicking the current star now waits the double-click interval** (the system setting, about 0.25–0.5 s) before it clears. That is the same wait every star click had before this task; setting a rating is instant.
   - The alternative is an instant clear. A double-click on the current star would then flash 3 → 0 → 3, and in a rating filter the photo would drop out of view.
   - I took the conservative option.
2. **A sidecar Phocasa can't parse is never written.** That includes empty (0-byte) and UTF-16 sidecars.
   - The rating still changes in Phocasa's library, but that RAW's file doesn't get it, and nothing says so.
   - The alternatives are to show the skip in the UI, or to back the file up and replace it.
3. **JPEGs the splice can't handle safely** (see the fallback list) still get today's full ImageIO rewrite, which loses the MakerNote and so on.
   - The alternative is to skip the metadata write for such files.
   - I kept today's behaviour, so ratings still reach those files.

- **Other formats.** HEIC, TIFF and PNG write-backs still use ImageIO's full rewrite. Check whether they drop maker notes too.
- **Silent failures.** Write-back failures and skips (unparseable or read-only sidecars, failed JPEG writes) are still silent; `SidecarWriteResult` makes them easy to surface.
- **Sidecar read cost.** A fast path for sidecars Phocasa wrote itself would help if first scans of large RAW libraries with sidecars matter. It costs about 0.1–0.2 ms per file now.
- **Large XMP.** A JPEG whose XMP needs Extended XMP (over 64 KB) takes the fallback path; that's rare.
- **Log noise.** ImageIO logs `CGImageDestinationCreateWithData: invalid capacity (0)` for every JPEG write, on `main` too: `CopyImageSource` needs a destination created with count 0, and it works. Harmless.
- **Pending clear in the detail view.** The deferred clear lives in `RatingView`'s state, so it still fires if the view goes away within the interval, for example on navigation. The user's click applies to the photo it was on, which is the intent.
