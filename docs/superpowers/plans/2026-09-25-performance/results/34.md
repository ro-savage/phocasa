### How it works

- **Re-key after a metadata-only rewrite.**
  - `MetadataWriter.perform` wraps `.metadata` writes to non-RAW paths in
    `rewriteObserver.rewritingMetadata(ofImageAt:) { service.writeMetadata(…) }`.
  - `ImageLoader`'s implementation (only when it has a disk cache):
    1. reads the per-path generation and `Version.current` (one `stat`);
    2. runs the write;
    3. stats again.
  - It re-keys only if all of these hold:
    - the version changed;
    - the modification date moved by less than 10 µs. `MetadataService` puts the date back, but `restoreFileDates`
      goes through `Date` and rounds APFS's nanoseconds to microseconds: measured on 200/200 fresh files, off by at
      most 620 ns;
    - no `invalidate(path:)` happened since step 1.
  - The `rekey` is queued while holding `generationLock`, like the loader's stores, so it is ordered against them and
    against a later `invalidate(path:)`'s removal.
  - On the queue:
    - every `<bucket>-<old>.jpg` of the photo is renamed to `<bucket>-<new>.jpg` (`rename(2)`);
    - an existing new-version file wins, and the old one is deleted and uncounted;
    - `old → new` is remembered for the path (chained, capped at 1,024 paths), so a store for `old` queued later is
      filed under `new`. That store comes from a decode that read the size before the write and finished after it;
      its pixels are the same.
  - `removeAll(forPath:)` forgets the path's re-key.
- **Smaller buckets from larger ones.**
  - On an exact disk miss, buckets `> b` and `≤ 2b` are tried in ascending order (the memory cache's rule).
  - The first hit is decoded down with `CreateThumbnailFromImageAlways` + `ThumbnailMaxPixelSize = b`. The memory
    cache then holds the requested bucket's size, as a fresh decode would.
  - Nothing new is stored; the larger file keeps serving.
  - A photo with no cache folder skips all of this after one `access` call.
- **Byte total.**
  - The file is `<dir>/byte-total`: five little-endian words (magic, format, bytes, verified-at, and a check word over
    bytes and date).
  - It is written after every change on the utility queue: one `pwrite` of 40 bytes on a descriptor kept open.
    - If the file was deleted from outside (`fstat` → `st_nlink == 0`), it is recreated.
    - It is truncated to 40 bytes when opened.
    - If the directory is gone, nothing is written until a store recreates it.
  - On a new instance's first queue operation:
    - no directory → the total is 0, verified now;
    - otherwise the record is used if it is intact, not negative, and its last full scan is between 7 days ago and
      1 hour ahead;
    - otherwise `knownBytes` stays nil and the next trim scans, as on `main`.
  - A full scan sets verified-at to now. So any drift the running total can't see (a crash between a write and its
    total, an older build adding files) lasts at most a week.
  - Deleting files from outside makes the total too high, which only brings the next scan forward.

## Deviations from the task file

1. **"Only when the old key matches" is by version, with a 10 µs tolerance on the date.**
   - `rekey` moves only files named with exactly the pre-write version.
   - The date check allows 10 µs. On APFS, `restoreFileDates` rounds the nanoseconds to microseconds (probe:
     200/200 fresh files moved, by up to 620 ns), so an exact check would refuse most re-keys of files with
     nanosecond dates.
   - A side effect: a rewrite that changes only the sub-microsecond part of the date is re-keyed too. On `main` that
     rewrite misses.
2. **Stores for the old version queued after the re-key follow it** (not in the task). A decode running during the
   rating (a batch rating while the first screen is still decoding) would otherwise store under the old key, delete
   the re-keyed files as stale, and miss next launch. It is bounded to 1,024 paths; losing an entry costs one decode.
3. **The re-key is also skipped when `invalidate(path:)` happened during the write** (the per-path generation).
   `testRewriteDuringWhichThePathIsInvalidatedIsNotRekeyed` pins it.
4. **Smaller from larger: decoded down, and nothing stored.** Measured above.
5. **Byte total: written after every change** (a `pwrite` on an open descriptor), not periodically.
   - A periodic write would lose the last stores of every session and let the total undercount, so the cache would
     grow past its limit over many launches.
   - "Plausible" includes a check word and a 7-day limit since the last full scan, which bounds any drift.
   - A new directory starts at a known 0, so a new cache never scans until it is over the limit.
6. **`mayHaveThumbnails(forPath:)`.** Added after measuring, so the cold miss is one failed call (cheaper than
   `main`'s).
7. **Wiring.** `MetadataWriter.shared` builds its observer from `ImageLoader.shared` in `MetadataWriter.swift`. The
   observer is a `nonisolated let` so the wiring can be tested.
8. **`DetailNavigationBenchmarks`** keeps the "old loadFullResolution" label, with the removed method's code inline.
9. **Real-file benchmark copies** go into the test's own temp folder (`ThumbnailDiskCacheBenchmarks-<uuid>`, deleted
   in `tearDown`), like every other test's temp data, not into `$TMPDIR/phocasa-34-*`. The copies are made writable:
   `~/PhocasaBenchRAW`'s files are read-only, and `MetadataService` skips read-only files.

- **`restoreFileDates` rounding** (above) is `MetadataService`'s. Apart from metadata writes, it only affects exports,
  which invalidate anyway.
- **Out of scope:** a Settings "Clear thumbnail cache" command, and the `Tools/imagebench` mirror, which still knows
  nothing of the disk cache.

## Couldn't verify

- The running app (not launched, per the rules). The coordinator checks it.
- Quiet-machine numbers. The load average was 1.6–13.7 throughout.
- Filesystems other than APFS: exFAT, SMB, HFS+ date granularity. Their stored dates are coarser, so restoring them
  should be exact. Not tested.
- Two cache instances or processes sharing one directory. Documented as unsupported; the 7-day scan bounds the drift.
- Page-cache-cold reads of the cached files.
